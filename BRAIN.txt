FIX 1 — BLOCKING SOMEONE ELSE. `implementation` is prose, not code.

  The live CODE artifact came back as:

    implementation: "Invoke the project's test suite and return True only if
                     it exits 0; block any completion/done claim until that
                     succeeds."

  contracts.py says: `implementation: str  # python source, executed in a
  Daytona sandbox`. lanes/code/materialize.py will take that string and try to
  run it. It is a description, so it will fail — at integration, not now.

  Fix in allocator/prompt.txt, not in code. The artifact spec must state that
  `implementation` is executable Python source: a complete function definition
  matching `signature`, importable and callable with no side effects at import,
  returning the value the signature promises. Give it a one-line example in the
  prompt so the shape is unambiguous.

  Re-run the tests case afterwards and confirm `implementation` is code you
  could paste into a file and run.

FIX 2 — the retry is a no-op.

  allocate() calls with temperature=0 and retries the IDENTICAL request. A
  deterministic parse failure fails identically the second time, so the retry
  buys nothing.

  On the retry, append the parse error to the user message — e.g. "Your previous
  response could not be parsed: <error>. Return only the JSON object." Then the
  model has something to correct. Keep temperature at 0.

  While in there: the `except AllocationError: raise` branch inside the loop is
  dead. _client() is called outside the loop, so nothing inside can raise it.
  Remove it.

THEN — batch mode, for the twenty labels.

  allocator/batch.py

    python -m allocator.batch labels.csv

  Input CSV columns: agent_said, user_wanted, situation, recurrence, expected
  ("expected" is the human label: code | weights | context).

  For each row, call allocate(). Print a row per correction: expected, actual,
  agree/disagree, confidence, rationale. Then print the agreement rate as a
  percentage and a confusion breakdown (which lane got confused for which).

  Run rows concurrently — twenty sequential grok calls is minutes of waiting
  and the prompt gets iterated many times today. A thread pool is fine.

  A row that raises AllocationError is printed as an error row and counted as a
  disagreement. Do not let one bad row kill the batch.

  This produces the agreement-rate number that goes in the video, and it is the
  loop for iterating prompt.txt against real data. It matters more than the gate.
